# Розтин провалу реального ІТ проєкту

Студент: Марний Данило MarnyiDanylo. Тема проєкту: Мобільний застосунок розкладу академії зі сповіщеннями про зміни.
Кейс: Міграція IT-платформи банку TSB (квітень 2018, Велика Британія).

## 1. Кейс і контекст

У квітні 2018 року британський банк TSB проводив міграцію з орендованої системи Lloyds Banking Group на власну платформу Proteo4UK, яку створював IT-провайдер материнської групи Banco Sabadell - компанія SABIS [SRC-01], [SRC-02]. Перехід охоплював перенесення даних близько 5,2 млн клієнтів протягом одного вікенду 20–22 квітня 2018 року [SRC-02]. Одразу після запуску цифрові канали зазнали масового колапсу: клієнти не могли увійти в систему, бачили дані чужих рахунків, телефонні лінії та відділення перевантажилися [SRC-02]. Збій тривав кілька місяців, а банк повернувся до нормальної роботи лише 10 грудня 2018 року [SRC-02]. Банк отримав 225 492 скарги від клієнтів [SRC-02], витрати через наслідки міграції склали £330,2 млн [SRC-01], генеральний директор Пол Пестер залишив посаду у вересні 2018 року [SRC-01], [SRC-03], а регулятор FCA призначив банку штраф у £29,75 млн [SRC-02].

## 3. Патерни провалу і кореневі причини

### Патерн 1: Big bang реліз

Подія таймлайну: Початок Main Migration Event (2018-04-20).
Замість поетапного переведення користувачів банк обрав єдиний релізний вікенд для міграції всієї клієнтської бази та корпоративних операцій на платформу Proteo4UK [SRC-02]. Через повну відмову від платформи LBG архітектура не передбачала технічної змоги швидкого відкату назад у разі виникнення непередбачених помилок, що спричинило загальнонаціональний колапс обслуговування [SRC-02].
Коренева причина: Вибір безальтернативної архітектурної стратегії запуску всієї інфраструктури без механізмів паралельного функціонування або безпечного відкату транзакцій [SRC-02].
Рівень причини: технологія.
Цитата з джерела: "Sabadell's existing methodology for IT migrations was to use a 'big bang' or single operation data migration approach, under which all data would be migrated in a single main migration event weekend" [SRC-02].

### Патерн 2: Пізня інтеграція і тестування

Подія таймлайну: Відмова від тестування в Active-Active конфігурації (2018-02).
Через затримки розробки та побоювання створити перебої для вже запущених сервісів банк відмовився від тестування цифрових каналів під навантаженням одночасно на двох дата-центрах [SRC-02]. Конфігурація балансувальників навантаження та модуля безпеки сесій OpenAM ніколи не перевірялася у бойових умовах, через що після запуску запити користувачів хаотично потрапляли на протилежні ЦОДи й руйнували сесії [SRC-02].
Коренева причина: Організаційне рішення вилучити ключове наскрізне тестування конфігурації дата-центрів із плану релізу без аналізу ризиків задля збереження фіксованої дати запуску [SRC-02].
Рівень причини: процес.
Цитата з джерела: "TSB failed to properly identify and evaluate the risks of not conducting testing of the digital channels in Active-Active configuration, only identifying the risks to disruption of services which were already online which would be caused by testing in Active-Active" [SRC-02].

### Патерн 3: Бажані оцінки замість реалістичних

Подія таймлайну: Запуск системи за непідтвердженими запевненнями вендора (2018-04-22).
Керівництво TSB покладалося на оптимістичні листи про наміри та суб'єктивні оцінки підрядника SABIS і субпідрядників, не вимагаючи фактів фактичного виконання та перевірених звітів про готовність [SRC-02]. Запевнення сприймалися як достатні підстави для релізу, попри наявність незакритих дефектів і відсутність робочого інструменту перевірки архітектури [SRC-02].
Коренева причина: Некритичне прийняття управлінською ланкою декларативних заяв постачальника без незалежного підтвердження фактів готовності перед ухваленням рішення Go-Live [SRC-02].
Рівень причини: люди.
Цитата з джерела: "The letter from SABIS and the fourth party confirmations were to some extent forward looking statements of good intention or expectation rather than statements of fact about the completeness of readiness activities undertaken" [SRC-02].

## 5. Перенесення на власний проєкт

### Ризик 1

Формулювання: Одномоментний запуск мобільного застосунку для всіх факультетів і курсів академії 1 вересня призведе до відмови серверної частини API через піковий наплив користувачів під час першої пари.
Виведений із патерну: Big bang реліз.
Ранній сигнал: У графіку запуску на ЛР7 відсутній етап пілотного тестування на 1–2 академічних групах, заплановано єдину дату публікації застосунку для всіх студентів.
Власник: PM / Release Engineer.

### Ризик 2

Формулювання: Інтеграційні тести між бекендом застосунку та API бази даних розкладу відкладаються на фінальний тиждень перед здачею, через що несумісність форматів даних змін аудиторій виявиться після публікації.
Виведений із патерну: Пізня інтеграція і тестування.
Ранній сигнал: Завдання розробки парсера та інтеграції в беклозі на ЛР6 мають пріоритет «Later» або відсутні критерії Definition of Ready щодо контрактів передачі даних.
Власник: QA Engineer / Backend Developer.

### Ризик 3

Формулювання: Розробник запевняє, що сервіс надсилання push-сповіщень протестований, але перевірка виконувалася лише на одиничних тестових повідомленнях, що призведе до затримок або падіння черги сповіщень при масовій розсилці.
Виведений із патерну: Бажані оцінки замість реалістичних.
Ранній сигнал: Оцінки задач на ЛР8 (Planning Poker) не враховують навантажувального тестування брокера черг сповіщень під час занять.
Власник: Team Lead / PM.

## 6. Робочий журнал

Первинні спроби знайти точні технічні причини через оглядові статті в інтернеті та неофіційні публікації дали лише поверховий переказ про "проблеми з серверами". Для отримання верифікованих даних було завантажено та проаналізовано офіційне рішення регулятора FCA (Final Notice 2022), річний фінансовий звіт банку TSB (Annual Report 2018) та матеріали розслідування Британського парламенту (HC 224). Це дозволило отримати точні параметри збою, зокрема конфігурацію Active-Active load balancing, суму прямих збитків у £330,2 млн та підтверджені дати регуляторних штрафів і кадрових рішень.
