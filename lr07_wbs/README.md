## 1. Стеля годин мого варіанта

| Роль | Зайнятість | Годин до релізу | Скільки взяв у WBS |
| --- | :-: | ---: | ---: |
| PM | 25% | 80 | 75 |
| Dev | 100% + 50% | 480 | 430 |
| QA | 50% | 160 | 100 |
| **Разом** | **2.25** | **720** | **605** |

Розрахунок: 2.25 * 8 тижнів * 40 годин на тиждень дає 720 годин команди до першого релізу. У корені `wbs.csv` стоїть 605 годин, це 84.0% відсотків стелі.

Чому саме стільки: Сума годин у корені WBS становить 605 годин, що складає 84.0% від максимальної ємності команди (720 год). Залишок у 115 годин свідомо збережено як буфер на випадок ризиків інтеграції із серверним API деканату та усунення дефектів під час приймального тестування.

## 2. Правило 100%: як перевіряли

Спосіб перевірки: Перевірку здійснено шляхом арифметичного підсумовування оцінок дочірніх вузлів для кожного батьківського пакета (сума листків рівна батьківським вузлам другого рівня, а сума другого рівня рівна кореневому вузлу `1`). ## 4. Критичний шлях

Дата старту робіт: 2026-08-24.

| Що | Значення |
| --- | --- |
| Критичний шлях, робочих днів | 65 |
| Ланцюг критичних робіт | T-01 -> T-02 -> T-04 -> T-05 -> T-07 -> T-11 -> T-12 -> T-13 |
| Дата завершення за планом | 2026-11-20 |
| Строк мого варіанта, робочих днів | 40 |
| Різниця | +25 днів |

Чи вкладаємось: Ні, розрахований критичний шлях (65 днів) перевищує директивний строк варіанта V01 (40 робочих днів / 8 тижнів).

Що з цим робимо: Для дотримання рамки першого релізу розширені функції - вибір періоду кешування (`S-15`) та експорт у системний календар (`S-10`) - свідомо винесено до релізу `REL-2`. Базову історію кешування `S-08` залишено у `REL-1`, проте її визначено як першого кандидата на винесення у `REL-2`, якщо під час розробки буде перевищено ємність спринтів. Одночасно залучається другий розробник Dev (50%) для паралельної розробки серверного API, що вивільняє головного розробника для виконання завдань критичного шляху.

Робота з найбільшим резервом: `T-03` (Розробка плану та журналу ризиків) та `T-10` мають резерв 34 дні, оскільки вони виконуються PM паралельно з розробкою і не блокують релізний конвеєр.
